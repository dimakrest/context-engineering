Your first flow: the smoke chain on real Orca

One PR, five Sonnet workers, a question, a failure and its retry, a script step and a gate, in about three minutes. Every command below was run on real Orca (1.4.223) on 2026-10-09 but three, each marked "not run in the pilot": the plugin install line and the skills /flows:flow-report and /flows:flow-plan. The outputs are what it printed, with this machine's paths replaced by variables. FLOWS.md next to this page is the reference.

4 · The walkthrough

1

The state directory and the Run

export SCRATCH=$HOME/.cache/flows-pilot ROUTER_STATE=$HOME/.cache/flows-pilot/state
mkdir -p $SCRATCH/out
orca orchestration run-create --objective "flows M5 smoke pilot" --json
python3 $R init
OK run run_1700985b87e4 · mailbox daemon pid 41608 · state $ROUTER_STATE
2

A throwaway worktree for the workers

orca worktree create --name flows-pilot --repo path:<the repository's main checkout> \
  --base-branch origin/orca-router --setup skip --no-parent --json
# result.worktree.path is the PR's WT. --repo path:<a linked worktree> answered repo_not_found
3

The flow file

One PR on router/templates/smoke.json with the python profile, one slot, start auto. The PR carries the template's steps with one addition, "worktree": "path:{WT}" on each worker step, so the workers run in the throwaway worktree instead of the coordinator's.

{"title": "M5 smoke pilot on real Orca", "slots": 1, "start": "auto",
 "templates": {"smoke": "<FLOWS>/router/templates/smoke.json"},
 "profile": "<FLOWS>/router/profiles/python.json",
 "vars": {"OUT": "<SCRATCH>/out"},
 "prs": [{"id": "smoke1", "part": "Pilot", "title": "The smoke chain in the throwaway worktree",
          "base": "orca-router", "after": [], "template": "smoke", "vars": {"WT": "<the worktree's path>"},
          "steps": [the six steps of smoke.json; alpha, beta, ask and flaky with "worktree": "path:{WT}"]}]}

<FLOWS> and the others stand for absolute paths, written out in the file.

4

Dry-run, then apply

python3 $R flow apply $SCRATCH/flow.json --dry-run
OK flow v0 -> v1, dry run, nothing written: 2 changes
  - flow created: 1 PRs · slots 1 · start auto
  - smoke1 added
python3 $R flow apply $SCRATCH/flow.json --by m5-worker --note "the M5 smoke pilot"
OK flow v1: 2 changes
  - flow created: 1 PRs · slots 1 · start auto
  - smoke1 added
  started smoke1 (v1), runner pid 44003

Under "start": "auto" the apply starts every ready PR. A refused file prints NOT OK flow: <n> problem(s), nothing changed and one line per problem.

5

Open the page, then wait

python3 $R page --open
http://127.0.0.1:63056/

python3 $R flow show
flow v1 · slots 1/1 · start auto · M5 smoke pilot on real Orca
  smoke1 · Pilot · The smoke chain in the throwaway worktree · after - · running alpha ∥ beta
python3 $R wait --timeout-min 8   # the coordinator runs it in the background, as the last action of every turn
6

Answer the three rings

WAKE question · smoke1 · ask · task task_bcd309132583 · dispatch ctx_409328483c78 · message msg_8dd7dea7db5e
question: Which word goes into ask.txt: PASS or FAIL?
python3 $R reply msg_8dd7dea7db5e PASS

WAKE failed · smoke1 · flaky (attempt 1)
worker_done failed: failed: no note attached
python3 $R retry smoke1 --note "write the word OK into flaky.txt in the target directory"

WAKE gate · smoke1 · accept: smoke gate: the lines below are what the coordinator would read
OK alpha.txt: 1 lines
OK beta.txt: 1 lines
OK ask.txt: VERDICT: PASS
OK the answer recorded by the script step: PASS
python3 $R resume smoke1

python3 $R status
smoke1  done · 6/6 steps
logs    5/5 settled dispatches collected

6 · The page, and an edit on it

While ask waited for its answer, the steps after it were pending, so they could move. In the Orca tab, with Orca's browser commands (the refs come from orca snapshot):

orca snapshot --page <page id>                       # refs: "Edit the flow", each step chip
orca click --page <page id> --element <Edit the flow>
orca drag --page <page id> --from <flaky chip> --to <record chip>
orca click --page <page id> --element <Apply…>        # "Apply to v1: the router will make v2 with 1 change"
orca fill --page <page id> --element <why> --value pilot-drag-1
orca click --page <page id> --element <Apply as v2>   # the header now says flow v2

A second drag on the same page, with no reload, put record back before flaky and applied as v3. Both reached the daemon: router.py flow history lists v2 and v3 by page, and the page's header showed the new version after each. A drop on a locked chip (🔒: done or running) is refused on the canvas.

7 · Collect and report

python3 $R collect --all --force
OK collected 5 · skipped 0 · locked 0 · not settled 0 · failed 0
python3 $R collect --dry-run
dry run: 5 settled dispatches · unique 5 · ambiguous 0 · none 0 · not settled 0 · failed 0 · nothing copied
python3 $R report --metrics $ROUTER_STATE/metrics.json
OK report $ROUTER_STATE/report.html · 1 PRs · 5 dispatches (0 ad hoc) · 5 collected sessions
orca tab create --url file://$ROUTER_STATE/report.html --json

The daemon had already collected each worker as it was released, so collect --all after the run only skips (it printed skipped 5 then); the line above is --force, which collected them again after a fix of the session matcher. Five workers in one worktree within three minutes had made four matches ambiguous; each session's first message names its own dispatch, and that now decides.

The gate lesson is the raw wait, how long the owner took to answer. The split's "at gates" takes off any second a worker ran, so on a bigger run the two can differ. /flows:flow-report (not run in the pilot) reads this table back; /flows:flow-plan (not run in the pilot) uses it to plan the next run.

8 · Clean up

python3 $R stop --all
OK stopped: mailbox · workers are untouched; a stopped chain goes on with router.py resume <pr>
orca worktree rm --worktree path:<the worktree's path> --json

The smoke chain opens no PR. The state directory stays: it is the run's record, and the report can be built again from it at any time.
