1 · The mental model, in one picture

A mission separates three jobs that a single agent session normally blurs together: deciding what "correct" means, building it, and checking it. Each one runs in a context that cannot see the others.

1

You define done — with the planner, before any code exists. This is the part you cannot delegate.

2

Agents build it — one feature at a time, each in a clean context, each ending in a commit.

3

Blind agents grade it — against your assertions, having never seen how the code was written or why.

2 · Before you start — five minutes

Restart your Claude Code session

The six hooks were added to .claude/settings.json. Skills and subagents were picked up live, but whether hooks hot-reload from a mid-session settings edit is unconfirmed — restarting is the cheap way not to care.

Confirm the hooks are asleep

With no mission running they must do nothing. Ordinary work in this repo should feel exactly as it did yesterday — same git commands, same edits, no new messages. If you see a line starting with MISSION: before you have started one, something is wrong; jump to §8.

Decide the autonomy ceiling

For a first run: halt at every milestone. Loosening later is cheap; discovering you were too loose is not. The planner asks you this and records it in mission.md.

Decide a budget

A token ceiling the loop enforces by halting. Without a number, the honest answer to "what did that cost" is unknown — and you lose the baseline that tells you whether this is worth repeating.

Where it all lands. .missions/ is git-ignored, so run state never pollutes a diff. Product code goes onto a branch through normal commits. The contract is copied into docs/plans/<slug>-plan.md so a reviewer can see what "done" meant — and docs/plans/ is git-ignored too, so nothing here reaches a PR unless you put it there.

3 · Picking the first task

The first mission is an experiment about the workflow, not a delivery deadline. Pick accordingly: something real enough that the result matters, small enough that a bad run costs an afternoon rather than a sprint.

Good first missionBad first mission
3–5 features, one or two milestones Twelve features — that is two missions, and you will not learn twice as much
Low blast radius — no migration, no partner API, no billing path Anything that halts constantly for confirmation; you will spend the run babysitting
Arguable correctness — where you would have written a test plan anyway A mechanical refactor; a green suite already tells you everything
Already on the backlog, with an issue you can hand the planner A toy invented for the demo — it will not surface the frictions that matter
Rich in conversational assertions if you want to test the payoff case Something where the only assertions are "the function exists"
The honest recommendation for run one. Keep every assertion structural — provable by the test layers. Skip the behavior validator entirely. It is the most valuable part of this workflow on a voice platform and also the slowest, the most expensive, and the most likely to fail for environmental reasons that teach you nothing about missions. Prove the loop first, then turn on real calls with the second mission.

4 · The walkthrough

  1. Start the planneryou

    /missions:mission-plan  add per-account retry limits to the outbound dispatch sweep
              (or paste an issue number / description)

    It reads the project's own docs first, dispatches cheap read-only researchers for anything it needs from the code, then interviews you. Expect it to push back on scope. That is the job — a mission that is twelve features long is usually two missions.

    It will ask for: the goal in one sentence, the non-goals, the blast radius, what done looks like to a user, the autonomy ceiling, and the budget. The non-goals matter more than they sound: they are what stops a worker from "improving" something adjacent at 2am.

  2. It writes three files — and no codeautomatic

    .missions/outbound-retry-limits/
  mission.md     goal, non-goals, model seats, budget cap
  contract.md    A001..A0nn  ← the artifact
  features.md    F001.. → milestone, assertions, procedures

    It refuses to finish unless every assertion maps to a feature, every feature to an assertion, and every assertion carries a proof class. If it cannot close that gap it tells you which side is wrong rather than quietly papering over it.

    While phase is planning, the mission-contract-first hook physically blocks writes to product code. Not a reminder — a block.

  3. Read the contract. Properly.you

    Ten minutes here is worth more than anything you can do later. §5 is the checklist.

  4. Design the architectureyou start it

    /missions:mission-design

    Mandatory, and still no code. It fans out read-only researcher agents to find how this repo already does things — the closest analogue to each feature, layering, error handling, test conventions, the legacy pattern nobody should imitate — and writes design.md: guidelines D001.., each anchored to a file:line exemplar. Every worker is bound to its feature's guidelines, and the blind reviewers grade conformance against the same ids. Review it like the contract: after this, the machinery obeys it.

  5. Run the loopyou start it

    /missions:mission-run

    From here it drives itself: dispatch one worker, ingest its handoff, update state, repeat; at a milestone, validate. You supervise. You do not steer feature by feature — if you find yourself wanting to, that is a signal the contract was underspecified, and the fix belongs in the contract.

  6. Milestone — it stops and reportsautomatic

    With the ceiling set to "halt at every milestone" you get a report and a decision. §6 covers what happened during it.

  7. Check in any timeyou

    /missions:mission-status   → docs/plans/<slug>-status.html

    Assertion coverage by proof class, features, spend, what is running, what is blocked. Safe to run mid-flight; it only reads.

  8. New day, new sessionyou

    /missions:mission-resume

    Reconstructs position from disk and reconciles it against git — git wins any disagreement. This is the claim that the state files are real: nothing needed from anyone's memory.

  9. Terminal — branch and draft PRautomatic

    Runs whatever pre-merge sweep the project defines, updates the docs whose sources changed, then hands the branch to /missions:mission-pr-review: it opens a draft PR — with the contract and the assertion→evidence table as the description — and puts the whole branch through review for the first time: a simplify pass, the general code review plus the repo's adversarial-review skill in parallel, a read-only assessment of every finding, and an HTML findings report. Surviving findings become follow-ups; nothing gets fixed here. Then it stops. You merge.

5 · Reviewing the contract — your real job

Everything downstream faithfully builds and certifies whatever this file says. A wrong assertion does not get caught by the workers, the reviewers, or the validators — they will all agree with each other, produce green checkmarks, and ship the wrong thing.

Read each assertion against these six questions

AskWhy it matters
Is this observable behavior, or implementation? Could two engineers satisfy it with completely different code and both be right? "reset_streak() exists" is not an assertion — it is a design decision smuggled in as a requirement, and it locks the worker out of a better approach.
Would I actually care if this broke? Assertions nobody cares about consume validator time at every milestone and train you to skim the results.
Where is the negative case? Every "it works" needs its "it refuses / it fails safe" pair. Adversarial validators need something to bite on; a contract of happy paths grades a happy-path implementation.
If this touches data scoped to a user, tenant or account, is the leakage case written down? It is never implied. An assertion that is not written is not checked — and cross-boundary leakage is exactly the defect that passes every test in an implementation-shaped suite.
Is the proof class honest? A structural tag on something only a real call can prove means it will be marked proven by a unit test that does not actually test it.
What is missing entirely? The hardest and most valuable question. The planner writes down what it was told about. What did neither of you say out loud?
The planner hands you a shortlist. It ends by naming the two or three assertions it is least sure about. Start there — that list is worth more than the summary above it, and it is the closest thing you get to the machine telling you where it is likely wrong.

6 · What happens inside a milestone

The number to watch. At the end, the loop reports how many defects the blind reviewers caught that the workers' own tests missed. That figure is the honest measure of whether this workflow earns its overhead. If it is consistently zero, you are paying for ceremony — either the reviewers are too soft or the assertions are too easy, and both are fixable.

7 · When a hook blocks you

Every mission hook prints a line starting with MISSION: and explains itself. None of them is advisory. Here is the full set and what each one actually means.

MessageWhat happenedWhat to do
a writing agent is already active Two workers at once, or a stale marker left in state.md after a handoff landed. If a worker really is running, wait. If not, the loop skipped its bookkeeping — set **Active writing agent:** none.
progress is blocked by unresolved handoff issues A previous worker reported a problem and nothing has addressed it. Resolve it, or move it into followups.md deliberately. Clearing it without reading it is the one thing this hook exists to prevent.
this '<agent>' prompt contains handoff content A validator was about to be told what the author said about their own work. Strip it. If the validator genuinely needs that fact, it belongs in the contract or in state.md — not in the validator's prompt.
mission-validator-behavior prompt contains a diff The behavior validator was about to read the implementation. Give it the assertions and the environment. It proves things by using the system.
phase is 'planning' — no product code yet Something tried to write code before the contract was finished. Finish the contract. If planning really is done, set **Phase:** implementing and dispatch a worker — the orchestrator does not write product code itself.
no pushing / no merging during a mission Exactly what it says. Nothing leaves the machine on the loop's initiative. Push it yourself when you are satisfied.
--no-verify / --admin are never allowed An agent tried to skip a failing gate. Fix the cause. A bypassed check is a defect no validator will catch, because they trust the gate that got skipped.
commit message must start with the feature id A commit during implementing with no F00n: prefix. Add it. If it belongs to no feature, ask why it is happening mid-mission.
the handoff for F00n is not valid evidence Missing sections, commands with no exit codes, or a commit sha that is not in the repo. Fix the handoff before the next feature. It lists exactly what is missing.
They are asleep unless a mission is live. All six check first for a .missions/*/state.md whose **Phase:** is something other than done or halted; without one they exit immediately. That is the first thing the test suite asserts, for every hook, including against a state.md too mangled to parse.

8 · Stopping, pausing, and escape hatches

Pause for the day

Do nothing. State is on disk. Tomorrow: /missions:mission-resume.

Stop the mission

Set **Phase:** halted in state.md, with the reason. Every hook stands down; the branch and commits stay exactly where they are.

Finish and go back to normal

**Phase:** done. Or delete .missions/<slug>/ — it is git-ignored and the code is already committed on the branch.

Hooks blocking ordinary work

A stale mission directory is almost always the cause. ls .missions/, then set the phase to done or remove it.

The mission directory, when you want to look yourself

.missions/<slug>/
  mission.md       goal · non-goals · seats · budget cap
  contract.md      assertions + status + evidence   ← read this one
  features.md      F00n → milestone, assertions, procedures
  state.md         phase · active writer · open issues   ← edit this to steer
  handoffs/        what each worker did, and left undone
  validation/      per-milestone verdicts with evidence
  followups.md     defects, as features
  journal.jsonl    append-only event log

state.md is the steering wheel: it is what the hooks read and what every agent reads first. Editing it by hand is a legitimate, expected operation — that is why it is a markdown file and not a database.

9 · What will go wrong the first time

No mission has been run end to end. The hooks are unit-tested and the prompts are written, but the loop as a whole is unproven — so treat run one as a dry run whose product is a list of frictions, not a feature.

The contract will be too vague

The first few assertions you write will read like requirements, not checks. You will find out at the first milestone when a reviewer answers "cannot tell from the diff" three times. That answer is the system working, not failing.

Features will be sized wrong

A worker that needs to read twenty files to start was given two features. You will see it as a handoff that reports lots of "left undone".

Validation will fail on first pass

Every milestone, by design. Budget for it: the source architecture reports validation never succeeding first try, and roughly 60% of both time and tokens going to implementation.

The validators are themselves unvalidated

Nothing has yet confirmed that mission-reviewer catches a planted defect. Until a mutation suite exists — plant an off-by-one, a swapped ownership filter, a dropped await, measure the catch rate — treat a clean verdict as informative, not authoritative.

The failure mode to keep in mind. Every mechanism here increases confidence by construction: a contract, a blind check, a verdict table, a coverage percentage. If the validators cannot actually fail, all of that machinery is an expensive way to generate green checkmarks. The mutation suite is the guard against it, and it should exist before you trust a mission result you did not personally read.

Worth capturing as you go

  • Which assertions turned out to be wrong, and whether you could have known at planning time
  • How many defects the blind reviewers caught that the workers' own tests missed — the number that justifies the overhead
  • Where you wanted to intervene, and whether the contract or the prompts should have handled it
  • Tokens and wall-clock versus what the same task would have cost conventionally

The five things that are actually load-bearing

RuleIf you only remember one thing about it
Contract before codeTests written after the implementation confirm decisions; they do not catch bugs.
