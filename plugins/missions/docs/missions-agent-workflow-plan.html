1 · What we're actually building, and what we're not

The talk's product is Factory's Missions. We are not rebuilding a product. We are extracting the five or six mechanisms that make long agent runs not drift, and expressing each one in a Claude Code primitive we already have: skills, subagents, hooks, files, and git.

The mechanisms worth porting

  • Validation contract — correctness defined as assertions before code, so tests can't be shaped by the implementation.
  • Fresh context per unit of work — one feature, one worker, one clean window, ends in a commit.
  • Author never grades itself — verification always runs in a context that never saw the implementation.
  • Behavioral validation — drive the real system, not just the test suite.
  • Serial writes, parallel reads — only read-only work fans out.
  • Structured handoffs + progress gating — state is written down, and progress blocks on unresolved issues.
  • Logic in prose, not state machines — so better models improve the system instead of obsoleting it.

What we are explicitly not copying

  • 16-day unattended runs. Bell is a production voice platform with telephony side effects and DB migrations. Our autonomy ceiling is a mission that produces a branch and a draft PR, never a merge.
  • Cross-provider validation. He debiases by putting validation on a different model provider. Inside Claude Code we can vary model and evidence, not vendor — see §7.
  • A bespoke “mission control” UI. We get the same oversight from a generated status page plus the existing terminal views; building a UI is not the experiment.
  • A new framework. Everything below is files in .claude/ plus a state directory. If it can't be expressed that way, it's out of scope.
The one-line bet: the reason a single long agent session degrades is not model capability — it's that nothing forces the definition of done to exist before the code, and nothing forces the checker to be blind to the implementation. Missions is mostly those two constraints, mechanically enforced.

His five communication primitives map cleanly onto things this repo can already express. The mapping is the whole design; everything after it is detail.

3 · Architecture — state on disk, control in one loop

The mission is a directory. The main Claude Code session is the orchestrator loop; it never writes product code itself. Every artifact that matters survives a context compaction, a /clear, or a laptop reboot, because it is a file.

3.1 · On-disk layout

docs/plans/<slug>-plan.md            # human-facing plan (existing repo convention)
.missions/<slug>/                    # git-ignored run state
  mission.md       # goal, non-goals, constraints, model seat assignment, budget cap
  contract.md      # THE artifact — assertions A001..Annn, behavioral, impl-independent
  features.md      # F001.. → milestone, assertions covered, procedures, status
  state.md         # BROADCAST: phase, active agent, milestone, open issues, spend
  handoffs/F001.md # structured handoff, one per feature — schema-enforced by hook
  validation/M1-scrutiny.md · M1-behavior.md · M1-review-F00n.md
  followups.md     # features created by failed validation
  journal.jsonl    # append-only: every dispatch, verdict, commit sha, token estimate

.missions/ goes in .gitignore. Product code lands on a branch via normal commits; run state stays local. The contract is the exception — it gets copied into the plan doc so a human reviewer sees what “done” was defined as.

4 · Skills to build — the prose layer

This is where his “~700 lines of text” lives. Deliberately prompts, not code, so a better model makes the system better rather than obsolete. Three new skills are the walking skeleton; the rest are earned, not assumed.

/missions:mission-plan newphase 1

The highest-value artifact in the whole plan. Interviews the user, argues about scope, and emits mission.md, contract.md, features.md. Writes zero product code.

Hard rules it enforces:

  • Assertions are observable behavior, not implementation. “Calling X returns Y” — never “function Z exists”.
  • Every assertion is assigned to ≥1 feature; every feature lists the assertions it satisfies; union must equal the contract. It refuses to finish otherwise.
  • Each feature is sized to fit one clean context window and one commit.
  • Milestones group features so a validator has something coherent to exercise.
  • Names the model seat per role and a token/spend cap.

/missions:mission-run newphase 1

The driver loop. Reads state.md, decides the single next action, dispatches, ingests the handoff, updates state, repeats.

  • Dispatch exactly one writing agent; fan out read-only agents freely.
  • On worker return: validate the handoff, append to journal, refuse to advance if issues are unresolved.
  • At a milestone: fire both validators, then per-feature reviewers in parallel, then negotiate.
  • Halt-and-ask triggers: budget cap hit, same assertion failing twice, migration or telephony side effect required, contract found to be wrong.

/missions:mission-status newphase 2

The async-oversight piece — his “mission control”. Renders a single self-contained HTML page from state.md + journal.jsonl: assertions covered vs total, features done vs planned, spend vs cap, what's running now, last N handoff summaries, open issues.

Fits the existing house style for findings pages, so no new UI surface.

/missions:mission-resume newphase 3

Rehydrate after a compaction, a /clear, or a new day: read the mission dir, reconstruct position, verify the working tree matches the last recorded commit, then hand control back to /missions:mission-run.

Only needed once missions actually outlive a session. Don't build it in phase 1.

5 · Subagents to build

Same frontmatter shape as the existing .claude/agents/*.md (description, model, tools). The tool allowlist is a real control, not documentation: a read-only agent that physically cannot write is a stronger guarantee than a prompt asking it not to.

mission-worker newphase 1

Tools: Read, Write, Edit, Glob, Grep, Bash · Model: code-fluent tier

Contract with the loop: receives one feature id, its assertions, its procedures, and the broadcast state — nothing else. Implements, runs the relevant test layer, commits with the feature id in the message, writes handoffs/F00n.md. Never touches another feature. Never pushes.

mission-researcher newphase 1

Tools: Read, Glob, Grep, WebFetch/WebSearch · Model: cheap/fast tier

The only legitimate parallelism. Answers one bounded read-only question (“where is the alerting failure streak reset?”, “what does this partner API return?”) and returns a short answer, not a file dump. Largely the existing Explore agent with a mission-shaped return format.

mission-reviewer newphase 1

Tools: Read, Glob, Grep, Bash(read-only git) · Model: instruction-precise tier

Blindness is the whole point: prompt contains the three-dot diff for one feature and that feature's assertions. It must not receive the handoff narrative or the worker's reasoning. Returns a verdict per assertion plus defects. Fans out one per feature at milestone time.

mission-validator-scrutiny newphase 1

Tools: Read, Bash · Model: instruction-precise tier

Runs the static gate per repo rules — tests/unit/ and tests/integration/ via Docker Compose (never bare pytest tests/), ruff, mypy, tsc, eslint. Reports raw output and exit codes; makes no repairs. Repair is a worker's job, in a new feature.

mission-validator-behavior newphase 2

Tools: Read, Bash, bell_test MCP, Playwright MCP · Model: instruction-precise tier

The QA engineer. For voice: places a real call through bell_test and drives the scenario. For UI: Playwright per the existing E2E context doc. Checks contract assertions about behavior, not code. Expensive and slow by design — see §8 and §9.

Reused as-is reuse

database for any migration work a feature needs (it already knows the alembic rules); backend-engineer / frontend-engineer as the behavioral basis for mission-worker's prompt — likely the worker is a thin mission-aware wrapper over those, not a from-scratch persona.

Unconfirmed — must verify before phase 1 design freeze: whether a Claude Code subagent can itself spawn subagents. If nesting is unavailable or unreliable, all fan-out (researchers, per-feature reviewers) must originate from the orchestrator loop rather than from inside a validator. The architecture above already assumes the safe answer — fan-out from the loop — but the assumption should be tested, not carried.

6 · Hooks — the thin deterministic layer

His framing: missions provide the discipline, models provide the intelligence. In Claude Code the discipline is hooks. This repo already has the pattern — check-db-safety.sh, git-freshness.sh, plan-testing-strategy.sh — so these are additions in a known idiom, not new machinery.

HookEvent / matcherEnforcesPhase
mission-serial-guard.shPreToolUse · Agent Block dispatching a writing agent when state.md shows one active, or when open handoff issues are unresolved. This is “serial writes” and “progress blocks on issues”, mechanically.1
mission-contract-first.shPreToolUse · Write|Edit Block product-code edits while mission phase is planning. Makes “contract before code” impossible to skip.1
mission-handoff-schema.shSubagentStop Reject a worker return with no valid handoff file — all required sections present, commands and exit codes recorded.1
mission-commit-discipline.shPreToolUse · Bash Require a feature id in mission commit messages; block push, merge, --no-verify, --admin during a mission. Complements the existing repo rules rather than restating them.1
mission-journal.shPostToolUse · Agent Append dispatch, duration, and spend estimate to journal.jsonl — feeds /missions:mission-status and the budget cap.2
check-db-safety.sh existsPreToolUse · Bash Already blocks writes against dev/prod DB ports. Missions inherit it for free — a strong argument for keeping missions inside this repo's hook surface rather than an external runner.—
Design rule: if a constraint can be checked with a 20-line bash script, it belongs in a hook, not in a prompt. Prompts hold judgment; hooks hold non-negotiables. Everything in the table above is a non-negotiable.

7 · Model seats — and the honest limit

He assigns models per role and puts validation on a different provider so it isn't biased by the same training data. Inside Claude Code we cannot do the provider half. Rather than pretend otherwise, we substitute the two debiasing levers we actually control.

SeatWantsProposed defaultDebiasing lever we actually have
Orchestrator / plannerslow, careful reasoning Opus 5, high effort—
Workerfast code fluency Sonnet 5 (Opus 5 for gnarly features)—
Researchercheap, fast, bounded Haiku 4.5—
Reviewer / validatorprecise instruction-following Opus 5, high effort Context blindness — validator sees the diff and the contract, never the worker's reasoning.
Evidence independence — its verdict must cite a command it ran or a call it placed, not a code reading.
Worth stating plainly: context blindness plus evidence independence gets us most of what cross-provider validation buys, because the dominant bias in practice is “the agent that wrote it believes it works”, not shared pretraining. But it is a weaker guarantee than his, and we should say so rather than claim parity. His second point transfers intact, though: the structure lets weaker models succeed — which is the argument for putting workers on Sonnet and spending the budget on planning and validation instead.

8 · The Bell-specific adaptation that makes this worth doing

His behavioral validator clicks buttons in a web app. Ours places a phone call. That's not a downgrade — it is the single highest-leverage fit between this idea and this codebase.

Voice agent behavior is exactly the class of correctness that unit tests confirm and never catch: the code is right, the tests are green, and the agent still says the wrong thing, transfers to the wrong queue, or hangs up early. The repo already has the instrument — bell_test MCP (start_call, say, wait_response, play_audio, end_call) plus the pr-voice-test-plan and run-test skills. Missions supplies the missing half: a contract written before the code that says what the call must do.

Practical consequence: /missions:mission-plan must tag every assertion with its proof class, because that tag decides which validator runs and how much a milestone costs in real minutes and real telephony spend.

9 · Guardrails — what must never be autonomous here

No merge, no push

Repo rule already: never commit or merge unless explicitly asked. A mission's terminal state is a branch plus a draft PR. Enforced by hook, not by prompt.

No migrations against dev/prod

Ports 5435/5436 are read-only. A feature needing a migration routes to the database agent and, in early phases, halts for human confirmation.

Worktree isolation

Missions run in their own git worktree so a multi-hour run can't collide with the human's checkout — this repo already runs several worktrees side by side.

Hard budget cap

mission.md carries a token/spend ceiling; the loop halts at it rather than asking forgiveness. His own data — validation never passing first try, ~60% of tokens on implementation — says the cost is real.

Telephony spend ceiling

Behavioral validation places real calls. Cap calls per milestone; make the validator reuse a scenario suite rather than improvising new calls each run.

Two-strike halt

If the same assertion fails validation twice, stop and surface it. Repeated failure usually means the contract is wrong, and no amount of re-scoping fixes a wrong contract.

10 · Phasing — walking skeleton first

Each phase ends with a claim we can check. If a phase's exit criterion fails, that is information about the idea, not a reason to build the next phase anyway.

  1. Phase 0 — Manual dry run ~1 day, no code

    Pick one contained, already-scoped feature. Hand-write a contract before touching code. Run it with today's skills, manually keeping the discipline: fresh session per feature, a second session that only sees the diff for review. Record where it hurt and where it helped.

    Exit: we can say concretely which of the seven mechanisms earned its keep on a real Bell feature — before writing a single skill file. This is the cheapest possible way to be wrong.

  2. Phase 1 — Walking skeleton core

    Build: /missions:mission-plan, /missions:mission-run; agents mission-worker, mission-researcher, mission-reviewer, mission-validator-scrutiny; hooks serial-guard, contract-first, handoff-schema, commit-discipline. State dir + journal. No behavioral validator yet — structural assertions only.

    Exit: one real multi-feature task runs end to end unattended within a session and produces a branch whose diff a human agrees satisfies the pre-written contract, with at least one defect caught by a blind reviewer that the worker's own tests missed.

  3. Phase 2 — Behavior + oversight the payoff

    Add mission-validator-behavior (voice via bell_test, UI via Playwright), assertion proof-class tagging in /missions:mission-plan, /missions:mission-status page, journal-driven budget tracking.

    Exit: a mission catches a conversational regression that the full green test suite did not — the specific claim that justifies the whole investment for a voice platform.

  4. Phase 3 — Duration only if 1–2 pay off

    Add /missions:mission-resume, worktree isolation by default, multi-milestone runs spanning sessions, terminal steps wired to pre-merge / create-pr / wiki-ingest.

    Exit: a mission survives a context compaction and a restart with no human re-explaining state, and hands over a PR that passes pre-merge unaided.

11 · Testing strategy

Required by the repo's planning rules — and unusually load-bearing here, because a validator that never fails is worse than no validator: it manufactures confidence. Note this section was written inline rather than via the plan-testing-strategy subagent, since subagent use wasn't requested for this task.

LayerWhat we testHow
Deterministic parts
phase 1		 Hook scripts and the handoff/state schemas — the only genuinely testable code in this plan. Real unit tests under tests/unit/missions/: feed each hook crafted JSON on stdin and assert block/allow. Table-driven — a handoff missing exit codes must be rejected; a second concurrent writer must be blocked.
Validator sensitivity
phase 1		 The most important test in the plan. Does a blind reviewer actually catch a planted defect? Mutation-style: take a passing feature, inject a known defect class (off-by-one, swapped tenant filter, dropped await, inverted boolean), run mission-reviewer against the mutated diff and its assertions, measure catch rate. A validator below an agreed threshold is a bug in the prompt, and we should treat it as one.
Golden missions
phase 1		 Would a contract written up front have covered what the real change actually needed? Take 2–3 already-merged PRs, check out the parent commit, run /missions:mission-plan from the issue text alone, then diff the generated contract against what the merged PR really did. Measures planning blind spots without spending implementation tokens.
End-to-end mission
phase 1		 The loop holds: serial writes, gated progress, no push, contract coverage. One real task per phase, reviewed by a human against the phase exit criterion. Journal is the evidence.
Behavioral validator
phase 2		 That it fails when it should. Deliberately regress a conversational behavior on a scratch branch and confirm the voice validator flags it. Same mutation logic as above, one layer up — the negative case is the test, not the positive one.
Cost & latency
phase 2		 That the discipline is affordable. Journal-derived: tokens and wall-clock per feature, per milestone, per mission. Compare against the same task done conventionally. His numbers say validation always fails first — confirm our multiplier and decide if it's worth it.
Regression on prompt edits
phase 3		 That editing 4 sentences of the orchestrator prompt doesn't silently change behavior. Re-run the golden-mission and mutation suites as a checked-in eval whenever .claude/skills/mission-*/ changes.
The failure mode to watch for: every mechanism here increases confidence by construction. If we don't test that validators can fail, we will have built an expensive machine for generating green checkmarks. The mutation suites in rows 2 and 5 are the guard against that, and they should exist before we trust a single mission result.

12 · Decisions needed before Phase 1

1 · Does missions supersede implement / full-stack / debug?

Those three already orchestrate agents. Running two competing idioms is worse than either. Options: missions replaces them for multi-feature work and they stay for single-shot tasks; or they get refactored to call the mission primitives. Needs a call before we add a fourth orchestrator.

2 · What is the first real mission?

It should be multi-feature, low-blast-radius, and rich in conversational assertions so phase 2 has something to prove. Ideally something already on the backlog rather than a toy.

3 · Autonomy ceiling for phase 1

Halt for human confirmation at every milestone, or only on validation failure and the two-strike rule? Starting stricter and loosening is much cheaper than the reverse.

4 · Budget per mission

A number in mission.md that the loop enforces. Without it, the honest answer to “what did that cost” is unknown, and phase 2's cost comparison has no baseline.

5 · Can subagents nest?

Cheap to test, and it decides whether validators fan out their own reviewers or the loop does it. Should be answered in phase 0.
